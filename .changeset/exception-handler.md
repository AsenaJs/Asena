'@asenajs/asena': minor

`@ExceptionHandler` classes handle errors in one place across HTTP, in-process events and microservices. An `@ExceptionHandler` (from `@asenajs/asena/decorators`) is an ordinary IoC component; its `@Catch(...types)` methods receive the thrown value and an `ExceptionContext` whose `scope` is `'http'`, `'event'` (`@On`) or `'microservice'` (`@MessagePattern` / `@EventPattern`, with `kind: 'message' | 'event'`). The new `@asenajs/asena/exception` entry point exports `@Catch`, `@NotFound` and the context types (`ExceptionContext`, `HttpExceptionContext`, `EventExceptionContext`, `MicroserviceExceptionContext`, `ExceptionScope`, `ExceptionType`) - nothing else.

- **Resolution:** most specific wins - the thrown value's prototype chain is walked upward, the same test as `instanceof` (so `util.inherits`-style errors match too), and `@Catch(ValidationError)` beats `@Catch(HttpException)` beats `@Catch(Error)`. A branded `HttpException` from another copy of the package still matches `@Catch(HttpException)`. Several `@ExceptionHandler` classes may exist, but an exception type may be caught in one place only, and there is one `@Catch()` catch-all per application; both are checked at boot.
- **`@Catch()` is not `@Catch(Error)`:** the catch-all also receives non-`Error` throws (`throw 'boom'`). `ValidationError`, `HttpException` and the auth 401s reach `@Catch(Error)`, or the catch-all when there is none, unless a `@Catch(HttpException)` is declared - an info line at boot names the handler that will receive them.
- **The chain:** returning `undefined` declines. On HTTP a `@Catch` answers with a `Response`; a non-`Response` value is logged as an error and treated as a decline; a `@Catch` that throws is logged and declines. After every `@Catch` declines, `@Config.onError` answers, then the adapter default. When a `@Catch` answers, the framework logs the original error at debug level only - log it in the handler if it matters.
- **`@NotFound()`** answers a request that matched no route - a routing 404 never reaches `@Catch`. One per application; when it declines, `@Config.onNotFound` answers, then the adapter's 404.
- **`@MessagePattern`:** a value other than `undefined` - `null` included - becomes the reply; `undefined` rethrows the original error to the transport. An error the `@Catch` throws replaces the original failure, so the caller can be sent a sanitized error. A returned `Response` is an HTTP answer: it is declined with a warning naming the `@Catch` and `@MessagePattern` methods, so the caller sees the original failure.
- **`@EventPattern` and `@On` are observe-only:** a matching `@Catch` runs, but the original failure continues unchanged - rethrown to the transport (retry / DLQ policy applies) for `@EventPattern`, the `[EventDispatchService]` error line for `@On`. A returned value has no effect and logs a warning naming the `@Catch` method. An `@EventPattern` failure waits for the `@Catch` for 5 s at most before it goes to the transport.
- **No feedback loops:** a failure raised by work a running `@Catch` started (an event it emitted, an in-process message it published) does not reach `@Catch` again; the framework default handles it, with a warning. The guard follows the async call chain, not a message through a real broker.
- **`ErrorHandler` / `NotFoundHandler`** now type the decline: they return `Response | undefined` (or a promise of it).
- **Ready-made status exceptions** in `@asenajs/asena/adapter`, one `HttpException` subclass per common status (`BadRequestException`, `UnauthorizedException`, `ForbiddenException`, `NotFoundException`, `ConflictException`, `UnprocessableEntityException`, `InternalServerErrorException`, `ServiceUnavailableException` and more), each catchable by type and defaulting its body to the reason phrase.

`@Config.onError` and `@Config.onNotFound` are deprecated and will be removed in 1.0. They keep working as the last link of the chain and log a deprecation warning at boot.
